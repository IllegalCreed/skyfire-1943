# Skyfire 1943 本地与互联网多人

更新日期：2026-10-02。本文记录已确认的多人目标、实现依赖与待定规则。当前 v0.15 增加单人关卡样段，延续键盘改键与手柄操控；多玩家设备分配、分屏和网络会话均未实现，继续后置。

## 目标与确认范围

用户明确希望同时支持本地多人和互联网联机。本地多人可以由键盘与手柄、两个手柄，或同一键盘的两个区域操控；本地追尾必须分屏。互联网联机各用完整屏幕，不分屏。

2026-10-02 用户进一步明确开发优先级：单人体验先做完整，双人合作最后加入。支持目标不变，多人目前只保留设计边界；先做多人再做单人关卡的助理建议已被替换。单人阶段的候选工作见[开发顺序](DEVELOPMENT.md)。

人数沿用本轮前文的 2P 讨论，承接范围为双人合作；四人或更多人数、对战、同机多人再混合接入远程玩家，尚未提出或确认。以下合作细节仍需讨论，不把支持模式的确认当成所有规则已经定稿。

| 模式 | 横版与俯视 | 追尾 | 目标状态 |
| --- | --- | --- | --- |
| 单人 | 保留现有完整画面 | 保留现有独立飞行与观察 | 已实现基础，不因多人取消 |
| 本地 2P | 同屏两架飞机，共同交战 | 两个独立观察区，分屏 | 用户确认方向，未实现 |
| 互联网 2P | 每名玩家各用完整画面，共同交战 | 每名玩家完整独立视图，不分屏 | 用户确认方向，未实现 |

两名玩家操控各自的飞机。每架飞机跨三视角保留身份和应继承的状态，延续[玩法](GAMEPLAY.md)与[成长](PROGRESSION.md)的跨视角原则；多人不能变成两个互不相干的单人关卡。

## 本地控制器与玩家分配

| 组合 | 目标分配规则 |
| --- | --- |
| 键盘与手柄 | 键盘输入分配给一个玩家，指定手柄分配给另一个玩家 |
| 两个手柄 | 两个不同设备各对应一个玩家，不能同时控制同一架飞机 |
| 同一键盘两人 | 两套互不冲突的按键区域对应两个逻辑玩家，不依赖物理键盘数量 |

建议加入前有设备确认：按键 / 手柄按钮显示对应玩家的名字或编号；两人各自准备后启动。游戏提示随分配设备显示。具体菜单流程、默认按键与是否允许随时加入，属于待确认草案。

当前[单人输入实现](../src/input/player_controls.gd)将可重绑主键、备用方向键与一个选定手柄合并到一架飞机，范围见[设置与控制](SETTINGS.md)。多人输入仍需要拆成各玩家的移动、射击、特殊攻击和菜单操作；共享键盘不能继续使用这套合并逻辑。手柄采用各玩家设备分配和独立输入状态，共用键盘采用逻辑布局分配。

默认键位候选为 P1 的 WASD + F/G、P2 的方向键 + J/K，仅为讨论草案。最终应支持重绑定，并保留单人原有操作。需要用实际 Mac 键盘同时测试两人移动 / 开火，记录按键冲突和硬件同时按键限制；不能用模拟输入通过替代真实键盘验证。

手柄的按钮、摇杆死区与映射需要实际设备验证。接入 / 断开应有提示，设备重新连接后不能悄悄交换玩家；断开时暂停、继续等待或其他处理尚待选择。触发菜单的玩家与游戏操控设备的归属要清楚。

## 本地追尾分屏

分屏是用户已确认的本地追尾规则；左右或上下布局、各区分辨率和 HUD 大小仍需实际引擎验证。先前讨论的同屏领航 / 共用航向方案不作为当前本地追尾目标。

每个观察区需要独立的航向、高度、转向反馈、我机后视图、机头参考、汇聚点、能量 / 火力提示。P1 与 P2 相反转向或升降时，不争夺同一个观察变换。

双方看到的是同一组敌人、敌弹、船和补给。观察变换只改变各自看到的位置，不改变目标真实状态、路线进度或伤害。场景和任务段的视角类型保持一致；追尾中的观察方向可以独立。

以下是多人必须落实的既有空间边界，当前尚无多人实现：

- 敌机不能因离开一个观察区就全局删除。另一观察区仍能看到它时，应继续存在；也不能重新使用固定年龄清除可见敌机。
- 主炮弹组归属发射玩家，使用该玩家的机头参考和发射时瞄准。不能用 P1 的汇聚点替 P2 判定命中。
- 保留第 16～19 帧有效窗口、第 20 帧失效和有效距离；分屏缩放只影响绘制，不能乘进碰撞容错。
- 两人的海空观察各自保持一致，倾斜不拖景；高空云滚动、海面渐入和触海规则继续有效。
- 一人高空、一人低空时，水面可见性与攻击反馈需要按各自状态验证。船不能向看不见且没有预警的高空玩家发起攻击。
- 伙伴飞机要按相对位置和朝向表现，不能把所有伙伴视图都当作我机后视。

单人当前参数来源为[追尾飞行](../src/gameplay/chase_flight.gd)、[接敌](../src/gameplay/chase_encounter.gd)与[主炮](../src/gameplay/chase_gun.gd)。当前单人最多三组双弹、三架空中敌机和六枚对空敌弹；多人是否按个人或团队分配这些容量需另行实验，不自动把上限翻倍。

## 互联网联机目标

联机成品目标是不同地点的玩家通过互联网共同游玩。工程阶段的同机双实例或局域网通信可用于调试，但不构成公网联机验收。

玩家入口待选择：

| 入口方案 | 体验与依赖 | 状态 |
| --- | --- | --- |
| 房间码或邀请 | 创建 / 加入、等待与准备；需要公网会话服务，并处理不可直连的网络 | 推荐草案，待用户选择 |
| 主机 IP 直连 | 输入地址连接主机；公网可达性可能需要路由器端口配置 | 备选，待用户选择 |

参考[Godot 高层联网文档](https://docs.godotengine.org/en/stable/tutorials/networking/high_level_multiplayer.html)，引擎提供主机 / 客户端连接和通信能力，直接公网连接仍涉及路由器可达性。房间码、邀请、中继和玩家友好的连接错误反馈需要单独设计；不能把 API 接通当成这些产品流程已经完成。

公网服务供应商、部署账号、位置、费用上限与运维方式尚未选择或授权。本轮没有购买、开通或部署服务。专用服务器，或玩家主机配合房间 / 中继服务，两种架构均尚待确定。

用户随后明确后期 Steam 发布和 Mac＋Windows 支持方向。Steam 版优先评估 Lobby / 好友邀请与 Steam Networking 中继，作为推荐接入方案，尚未实现或选定具体绑定。网络验收包含 Mac ↔ Windows 跨系统互通；Remote Play Together 沿用本地布局，不能替代各自完整视图的原生联网目标。平台、接口预留与发布依赖见[发布计划](RELEASE.md)。

## 共同战斗与延迟处理草案

建议让本地与联网共用一套战斗模型，把玩家输入、战斗模拟和画面表现分开。本地将两个输入交给共同模拟；联网提交各自输入，并由统一的判定方确认关键结果。以下属于技术建议，尚未实现或完成手感验证。

- 玩家实体及弹组具有明确归属，双方共享敌人、目标耐久、波次、关段和补给实体。
- 敌人、子弹、掉落和关键事件使用稳定标识；重复消息不能重复击落、计分或掉落奖励。
- 本机移动 / 开火应立即反馈，再接收统一确认与必要校正；远端运动需要连续表现，不能直接跳坐标。
- 原有 60 Hz 模拟和四帧命中窗口约 66.7 毫秒。联网应记录模拟帧、发射时刻、瞄准和必要历史状态，验证延迟补偿；不擅自扩大有效窗口或改为自动锁定。
- 转场和重试处理双方状态；同一 Boss 和补给不能因换观察者、重连或切视角复活 / 复制。
- 版本不匹配、房间已满、连接失败、对方离开、主机退出和超时，都应有明确可恢复的界面状态。

延迟与丢包测试矩阵草案：往返延迟 0 / 50 / 100 / 150 / 250 毫秒，丢包率 0 / 1 / 3 / 5%，同时覆盖抖动与乱序。这是测试条件，不是已经验证的可接受上限；最终可玩条件应通过双端实际输入和画面核对确定。

## 单人与双人的敌人配置

状态：用户询问是否需要调整；以下是推荐方案，未实现，尚未确定任何双人倍率。目的：双人增加总火力、覆盖范围和分工机会后，仍有适当压力，同时保留单人击落节奏与攻击可读性。

建议关卡、敌种、造型和核心命中规则共用，波次配置按人数分别调校；人数与难度是两个维度，不能把双人直接等同于最高难度。先取得稳定单人基线，再制作双人配置，不从当前单人参数机械推导两倍值。

| 项目 | 单人基线 | 双人候选调整 |
| --- | --- | --- |
| 波次与组合 | 一人能读路线、射击、躲避和拾取 | 增加侧翼编队、配合敌种或错峰压力，避免全程把数量翻倍 |
| 普通机耐久 | 保留轻型机迅速击落与不同敌种的区别 | 不普遍翻倍；奖励快机保留快速、难瞄准的角色，具体耐久另测 |
| 舰船 / Boss | 耐久与可攻击窗口配合目标战斗节奏 | 可适度增加耐久或活跃炮位，仍要有安全空间和拆部件反馈，不让战斗单纯变长 |
| 火力与目标 | 攻击预警、弹速、间隔和躲避空档可读 | 分配或交替攻击两人，限制总火力，不把每枚攻击复制给两人或集中围攻一人 |
| 奖励与补给 | 一人的能量和火力成长预算 | 按最终归属规则重新预算总供给与出现时机，避免两人分单人份额而一人长期无法成长 |

三个视角分别验收：横版 / 俯视核对两机占据空间后是否仍有避弹路线；追尾核对两个观察区的目标可见性、弹幕密度与有效命中机会。当前单人三架空中敌机、六枚对空敌弹及三组我方双弹上限保持原样；双人容量按团队 / 个人如何分配仍待试验，不能直接翻倍，也不能扩大 16～19 帧窗口、缩小判定公平性或对可见敌机按年龄强删。

本地 2P 和互联网 2P 建议采用同一套双人战斗配置，区别在观察和输入方式；分屏还需额外验证可读性。是否允许中途加入、以及按参加人数还是存活人数调整仍未决定。如果未来允许动态调整，建议在后续波次 / 阶段边界切换，不即时重置现有敌人、Boss 部件或掉落，以免形成刷奖励和反复改难度的漏洞。

配置建议与目标分配是本轮讨论草案，不是当前游戏规则。验收需固定关段、难度和武器水平，对照一人 / 两人的击杀节奏、Boss 时间、避弹空间、资源获得与失败原因，再经真实双人试玩确认。多人扩展不得覆盖已有单人配置或把模拟输入通过当成平衡获认可。

## 尚需确定的合作规则

支持模式与控制器范围已经确认，以下尚未拍板：

- 能量、火力等级、弹种、护盾与特殊库存按个人独立，还是其中部分共用；各玩家跨三视角的继承仍须明确。
- 普通与奖励补给由拾取者获得，还是给两人共享；掉落数量是否调整。
- 一人能量耗尽或坠海后观战、有限复活或其他处理；全队失败条件和恢复保底。
- 个人分数、团队分数、击落归属和合作奖励的显示与结算。
- 双人碰撞、友军火力、暂停权、加入时机与中途离开的处理。
- 多人难度、敌人容量、双弹组容量、目标选择和补给供给。
- 本地分屏方向、界面密度、控制器重绑定与具体手柄验收机型。

上述选择不能从当前单份 `energy` / `power` 等变量推断为用户已同意共享，也不能把另一玩家简单当作自动僚机。

## 候选实施顺序与验收

以下只适用于单人体验稳定后的多人阶段，尚非已启动或已完成的版本，不覆盖[单人优先顺序](DEVELOPMENT.md)：

1. 建立两玩家身份、输入归属和共同战斗模型，保持单人回归。
2. 实验横版 / 俯视同屏、本地追尾分屏，用真实键盘与手柄核对三种输入组合。
   同时制作并验证独立双人波次 / 敌人配置，单人配置继续保留与回归。
3. 选定公网入口和服务架构，接入互联网会话、准备、离开与错误反馈。
4. 加入同步、延迟处理与重连政策，通过可控网络条件和实际异地双端验收。

完成标准包括：两人不会互相抢输入；追尾观察独立且目标状态唯一；有效命中、掉落、计分和恢复不重复；真实异地网络可连接并共同完成样段；导出 Mac 应用及必要服务分别记录版本与验证结果。没有公网实测时不得称互联网联机已验证，通过自动测试也不代表双人手感获认可。
