## 如何看状态

- **已实现**：当前本地原型中有对应代码。是否已测试、是否获得试玩认可，另行说明；不等于正式版完成。
- **设计方向**：对话中正在沿用的目标或约束，不等于所有细节已拍板，更不等于已经实现。
- **讨论草案**：提出过的具体方案，尚待选择或确认。
- **待验证**：数值、手感或可读性需要实际实验才能定下来。
- **已调整**：旧提案在设计层被替换；除非注明，不代表旧实现也已改掉。

各文档把当前实现与目标方案分开。道具数值、关卡波次、Boss 时长等草案数字不是代码配置，不能直接当作正式平衡参数。

## 当前项目概况

游戏围绕同一架飞机在横版、俯视、追尾三种空间中作战。长期目标是连贯战役，不是三款独立小游戏的拼接。当前可玩版本是手感实验室 v0.9，没有正式六关、Boss、存档或关卡检查点。

最近对话形成的设计方向包括共享装备成长、弹种选择、低空战术和追尾天气。具体玩法仍按各专题文档标注为草案或待验证；保存进文档不构成开发启动或实现完成。

## 维护方式

1. 讨论新机制时，先补入对应专题，并标明状态、影响的视角和待确认问题。
2. 调整旧方案时，直接更新专题中的当前方案；在[决策记录](DECISIONS.md)保留原因，避免互相冲突的版本同时成为规则。
3. 获准实现后，按专题的验收条件开发；涉及其他系统时同步更新交叉引用。
4. 实现完成后，再更新[开发进度](DEVELOPMENT.md)，记录对应代码、测试结果和仍未验证的部分。
5. 试玩反馈注明版本、视角、操作、预期与实际表现；不能只记录“手感不对”。

不要求每次对话都新建文件。先维护已有专题，内容确实独立且变长时再拆分。文档和代码保存在同一仓库，按用户授权进行提交与同步；本次迁移明确包含 GitHub 同步。迁移目录、备份和工具边界见[仓库说明](REPOSITORY.md)。

## 机制记录模板

新增机制按下列内容说明即可，不必填写无关字段：

- 目的与状态：解决什么问题，是方向、草案还是已实现。
- 玩家操作与反馈：怎么触发，看到什么，结果是什么。
- 共享与差异：跨关卡保存什么，三个视角哪些规则一致、哪些表现不同。
- 边界与依赖：不影响哪些既有规则，需要哪些系统先完成。
- 参数与验收：数值单位、代码来源或草案依据，以及如何证明功能有效。
- 待确认问题：哪些选择仍需项目发起人决定。
